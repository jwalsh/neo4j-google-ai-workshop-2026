#+TITLE: 002 - Form 13 as RDF, with Jena and SPARQL
#+DATE: 2026-10-08

* Source

Lab 4's day file, =data/form13-2023-05-11.csv= (7,381 rows, fetched by
=workshop.form13/fetch!=), and the property graph the lab makes of it:
=(:Manager)-[:OWNS {value, shares, reportCalendarOrQuarter}]->(:Company)=,
loaded by =labs/lab-04/03= to =06=. The figures to reproduce are those
=src/workshop/form13.clj= computes from the same file in memory.

The question was the owner's: what are related ways to hold this data, RDF
triples for one, and how is that explored from Emacs, CIDER and Clojure.

* Hypothesis

The same file held as RDF triples and asked in SPARQL gives the same
answers as the rows in memory, and the whole thing is drivable from a
Clojure REPL with nothing running but a JVM: Apache Jena by interop, an
in-memory model, no server.

* What was kept and what was left out

Kept: every row and every column. Managers keyed on name and companies on
CUSIP, as the lab's node keys are. The vocabulary is ten properties and
three classes under =http://example.org/form13/vocab#=, made up here.

The decision that matters. =OWNS= carries properties, and a triple has
nowhere to put them, so the relationship becomes a node (the n-ary relation
pattern). Abbreviated for reading; the file in =out/= writes this IRI in
full:

#+begin_src ttl
holding:M%26T%20Bank%20Corp/037833100/2023-03-31
        a                   f13:Holding ;
        f13:manager         manager:M%26T%20Bank%20Corp ;
        f13:company         company:037833100 ;
        f13:value           1054757624000.0 ;
        f13:shares          6396039 ;
        f13:quarter         "2023-03-31"^^xsd:date ;
        f13:sourceFilingId  "raw_2023-05-11_archives_edgar_data_36270_0000950123-23-004428.txt" .
#+end_src

The Holding's IRI is minted from manager, CUSIP and quarter, the key the
lab's =MERGE= uses for =OWNS=. The bare triple
=manager:... f13:owns company:...= is asserted as well, as a shortcut that
carries none of the above.

Changed from the lab's graph: a company keeps every name it was filed
under (the lab's =ON CREATE SET= keeps the first one it meets), and
=sourceFilingId= is kept (the lab's load drops it).

Left out: RDF-star as the load's model. =form13.rdf/annotated-example= is
one holding written with the properties on the triple itself, in Turtle 1.2
annotation syntax, and Jena 6.2.0 parses and queries it; the data is not
loaded that way. Also left out: any ontology (no RDFS or OWL, no
inference), named graphs, a persistent store (TDB2) or a SPARQL endpoint
(Fuseki), and any published vocabulary. =arachne-framework/aristotle= was
checked and not used: it has no release on Clojars, resolves only as a git
dependency (last commit 2025-01-27), and pins Jena 5.3.0.

* Run

=../../data/form13-2023-05-11.csv=.

* Property graph and RDF, for this file

From what was built here and what =labs/lab-04= loads, not in general.

- *The relationship with properties.* In Neo4j it is one =OWNS= edge with
  three properties: 7,381 relationships. In RDF it is a Holding node and
  seven triples, plus the bare =owns= triple: 59,048 of the 66,183 triples
  are holdings. Every query that needs a value or a share count goes
  through the Holding (=?holding f13:manager ?m ; f13:company ?c=) where
  Cypher writes =(m)-[o:OWNS]->(c)=. Degree needs no properties, and the
  bare triple answers it with the same top five.
- *One company, several names.* 258 CUSIPs were filed under more than one
  spelling. The lab's =MERGE ... ON CREATE SET c.companyName= keeps
  whichever arrives first and the rest are gone. A property in RDF is
  multi-valued unless something says otherwise, so =company:037833100= has
  three =f13:companyName= values and the name-variants question is a
  =GROUP BY ... HAVING= over data that is still there: 2,577 name triples
  for 2,251 companies. The cost is that "the company's name" is no longer
  one thing: =:managers-per-company= picks =MIN(?name)= in a subquery, and
  joining names straight into a =SUM= would multiply it.
- *Identity and idempotence.* In Neo4j identity is whatever the =MERGE=
  pattern names, backed by the two node-key constraints.
  =01-simple-load.cypher= merges Company on name and CUSIP together, so
  each spelling is its own node; =04-companies.cypher= merges on CUSIP
  alone. Here identity is the IRI,
  and a graph is a set of triples: adding every row twice leaves 66,183.
  What takes the place of the constraint is the function that mints the
  IRI, and nothing checks it: a second quarter would mint new Holdings
  correctly, but two managers whose names differ by a comma are two IRIs,
  as they are two nodes in Neo4j.
- *Types.* =toFloat(row.value)= in the lab; =xsd:decimal= here, so the
  value is exact in the file (=1054757624000.0=). Jena hands a whole-number
  decimal back to Clojure as a =Long= and the shares as an =Integer= or
  =Long= by size. The quarter is =xsd:date= in both.
- *Schema.* RDF has none imposed; Neo4j has the two node keys Lab 4
  made and nothing else. Labels and relationship types in
  Neo4j, =rdf:type= and predicates here; both can be listed from the data
  (=CALL db.schema.visualization()= there, two =GROUP BY= queries in
  =rdf_explore.clj= here). RDF's are global names, which is what would
  let this file be merged with someone else's by CUSIP; nothing here tests
  that.
- *Traversal.* "Managers who hold the same companies" is two hops either
  way: =(a)-[:OWNS]->(c)<-[:OWNS]-(b)= or two triple patterns sharing
  =?company=, or the property path =f13:owns/^f13:owns=. About a second
  in Jena's in-memory model on this file. SPARQL has no path values: it
  can say that two managers are connected, not return the path, which is
  what Lab 5's Bloom views are made of.
- *RDF 1.2.* With annotation syntax the edge-with-properties shape comes
  back: =manager f13:owns company {| f13:value ... |}=. Jena stores it as
  four triples (the triple, a blank reifier with =rdf:reifies=, two
  properties), so it is the Holding node again with the IRI left out and
  nicer syntax. Left out, the reifier is a fresh blank node per parse:
  reading the example twice into one model gives 7 triples and two rows
  from the query, so the idempotence above is lost. Naming the reifier
  (=~ holding:x {| ... |}=) gives 4 again, and is the Holding node.

* What it is not

Not exercised from Emacs. Nobody ran =cider-jack-in= here: that
=.dir-locals.el= is read, that CIDER takes this directory as the project
root and not the repository's, and that =C-x C-e= behaves as described are
all untested. What was tested is the layer beneath: the forms evaluate, in
process and over nREPL.

Not compared with the database. The gate's numbers are the file's; the
Aura instance was not queried, so "the same as the lab's graph" rests on
=form13/verify= having said the load matches the file, not on anything
here.

Not an ontology and not linked data. The IRIs are under =example.org= and
resolve to nothing; the vocabulary reuses no published terms (FIBO, for
one, has terms for holdings); nothing is inferred. Percent-encoded manager
names make IRIs that Jena's Turtle writer spells out in full, as it does
the Holding IRIs with their slashes; a real model would mint them from the filer's CIK, which is
inside =sourceFilingId= and was not parsed out.

Not a store. An in-memory model built in a quarter of a second from 7,381
rows says nothing about TDB2, Fuseki, or how either compares with Aura at
any size.
