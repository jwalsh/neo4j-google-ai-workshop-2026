* The thesis: RDF and logic programming are related triple stores

One row in all five forms: [[file:diagrams/one-fact-five-forms.mmd][diagrams/one-fact-five-forms.mmd]]. The family
and what moves between neighbours: [[file:diagrams/triple-stores-family.mmd][diagrams/triple-stores-family.mmd]].

The claim has three parts and they do not fare alike. (a) RDF and logic
programming are related. (b) Both come down to stores of triples. (c) So
what is learned in one carries to the other.

** Where they coincide, and it is exact

A fact is a tuple. An RDF triple is a ground atom of one three-place
relation. A datom is the same with a transaction on the end. A pldb fact
is a ground atom of a relation of any arity. A query is a join: a SPARQL
basic graph pattern, a Datalog =:where=, and a conjunction of miniKanren
goals are all the conjunctive query, with shared variables doing the
joining. A rule is a join with a name.

The experiments measured this and it held, on every number they share:

| question | 002 SPARQL | 003 Datalog | 004 miniKanren | rows |
|----------+------------+-------------+----------------+------|
| managers, CUSIPs, holdings | 28, 2,251, 7,381 | same, both stores | same | same |
| CUSIPs under several names | 258, =GROUP BY ... HAVING= | 258, cardinality-many | 258, =company= twice and =!== | 258 |
| top manager | Envestnet, 1,615 | same | same, asked two ways | same |
| holders of Apple | 22 | 22 (DataScript) | 22, asked two ways | 22 |
| manager pairs sharing a company | not gated | 281 | 562 ordered, which is 281 | 281 |
| Envestnet and Guggenheim share | not gated | in the 281 | 1,099 | 1,099 |

From the three READMEs and their gates, re-run for this review. The last
figure is also what the audit read from Aura in Cypher
(=.meta/audit-2026-10-08.md=, "share 1,099"), so on that one number four
engines and a =group-by= agree.

The named join held in two of three. DataScript's =co-holds= rule returns
the same 281 pairs as the inlined clauses (003, gate "rule = inline").
core.logic's =holdso= is two lines and =both-holdo= and =chaino= are built
from it (004). SPARQL has no rules. 002's property path
=f13:owns/^f13:owns= is one fixed shape of rule, not a way to write them.

The background, from general knowledge and not from anything measured
here: RDF's semantics is model-theoretic, the RDFS and OWL RL entailment
rules are Datalog rules, and SPARQL's expressive power is that of
non-recursive Datalog with negation (Angles and Gutierrez, 2008, as I
remember the citation). So part (a) is true and well known. What the
repository adds is that it survives contact with real libraries on real
rows.

** Where it is an analogy

*"Triple store."* The arity is the whole difference, and it shows in the
one place the experiments had to make a decision: =OWNS= carries three
properties.

| form | what the edge became | cost for 7,381 holdings | source |
|------+----------------------+-------------------------+--------|
| Neo4j | one relationship with properties | 7,381 relationships | =labs/lab-04/06= |
| RDF | a Holding node, 7 triples, plus the bare =owns= | 59,048 of 66,183 triples | 002 |
| RDF 1.2 | an annotated triple, stored as 4 with a reifier | the Holding again, IRI left out | 002 |
| DataScript | a holding entity, 7 datoms | 51,667 of 56,523 datoms | 003 |
| Asami | a node with two links and four values | 49,142 triples in all | 003 |
| pldb | nothing: =holds= has four places | 7,381 facts of 9,986 | 004 |

The 9,986 is my sum of 004's fact table (28 + 2,577 + 7,381). Note 51,667:
it is 7 by 7,381, the number of cells in the CSV, and it turns up in both
002 and 003. A triple store spells each cell out as its own fact and then
needs a made-up subject to hang them on. Reification, the holding entity
and the n-ary relation pattern are three names for that subject.

So the edge-with-properties problem is a problem of fixed arity three, not
of logic. Experiment 004 does not have it. I disagree with 003's README at
line 192, "the relationship with properties is the one thing the graph has
that the tuples lack": it is the one thing the graph has that
three-tuples lack. And 004 dropped the quarter and the filing id to get
down to four places, so its win is partly a smaller question.

*Identity.* Four regimes, and each failed differently on the same 258
CUSIPs or on the second source:

| form | identity is | what happened | source |
|------+-------------+---------------+--------|
| Neo4j, naive | whatever =MERGE= names: name and CUSIP | 2,577 companies for 2,251 CUSIPs | =notes/lab-04-query.org= |
| Neo4j, keyed | node key on =cusip=, =ON CREATE SET= | first name wins, the rest dropped, silently | 002, 003 |
| Neo4j, second source | the same node key | loud refusal: "must have the property cusip" | finding 24 |
| RDF | the IRI a function mints | all 2,577 names kept; nothing checks the minting | 002 |
| DataScript, obvious schema | unique attribute, upsert | last name wins: 0 variants, no error | 003, =lossy-schema= |
| DataScript, one word changed | the same, name made many | 258 | 003 |
| pldb | none: a term is its value | 2,577 =company= facts; every count needs =distinct= | 004 |

Finding 24 is the sharp one and worth reading against this table. The
constraint that refused the model's =Company= is the existence half of a
node key. A plain uniqueness constraint would have let a company with no
CUSIP in. So 003's table (line 178) is wrong to call Lab 4's schema "two
uniqueness constraints", and 002 (line 148) is wrong that "neither has
one imposed": Neo4j had two imposed, and they are what bit. In RDF the
same collision cannot fail. A second source mints its own IRI for Apple
and the two never meet: silent non-identity where Neo4j gave a loud
refusal. Neither is a join.

*Schema.* None (RDF, Asami, maps), per attribute (DataScript: five
declared), per label and key (Neo4j: two node keys, and now a uniqueness
constraint on =__Entity__.id=, from =SHOW CONSTRAINTS= run for this
review), per relation and position (pldb: =db-rel= fixes arity and which
places are indexed). They are not points on one scale. Cardinality is a
schema question in DataScript, a non-question in RDF, and not expressible
as a constraint in any of the others here.

*Index.* The word means three things.

- In a triple or datom store it is a sort order of the whole set. Arity
  three is small enough to keep several permutations, so any pattern with
  one place bound has an index. This is what "store" buys in "triple
  store". From general knowledge of Jena and DataScript; neither 002 nor
  003 looked at an index.
- In Neo4j it is per label and property, opt in, with a planner choosing.
  The audit lists a range index behind each node key and three vector
  indexes the Graph Builder made.
- In pldb it is one hash map per marked position and one index per call:
  the leftmost position that is both indexed and ground. No planner. 004
  measured it: the same join with =holds= stored manager first took 758.8
  ms and cusip first 8.2 ms; 886.9 and 8.7 when I re-ran the gate.
  Argument order is the query plan, and goal order is the rest of it (=!==
  moved after the two =company= calls: about 100 ms down to about 30).

That last one is where the analogy is thinnest. A logic database of n-ary
relations has no uniform indexing to fall back on. The author is the
planner.

** Where it is wrong

*Multiplicity.* "A query is a join" is true up to how many times an
answer counts, and the forms disagree:

| form | facts are | answers are | aggregates | what it cost here |
|------+-----------+-------------+------------+-------------------|
| RDF, SPARQL | a set: every row added twice, still 66,183 | a bag | in the language | joining names into a =SUM= would multiply it (002) |
| DataScript | a set | a set | yes, with =:with= | none once =:with ?holding= was written |
| Asami | a set | a set | yes | =sum= gave 9.6331905975E13 for 9.6335448383E13, silently (003) |
| pldb, miniKanren | a set | a bag, one per derivation | none | 37,632 answers for 562 pairs; 3 names for Westwood's 2 CUSIPs (004) |
| Cypher | a multigraph | a bag | in the language | none; =count(DISTINCT c)= where needed |

Asami's total is short by about 3.5 billion, which is exactly the
duplicate values: the set was taken before the sum. The right total is
also what =bb form13 summary= printed for this review. Same data, same
logical query, two answers, no error. Lab 5 is degree centrality, which
is a count, and 004 says plainly that the logic engine contributes
nothing to it. A thesis that puts SPARQL and miniKanren in one family has
to stop before aggregation.

*"Logic programming" is two things.* 003 is Datalog: no function
symbols, set semantics, always terminates. 004 is miniKanren: terms with
structure, search, bags, and no promise of ending. RDF's relatives are
the first kind. 004's =chaino= returns the path as a list, which neither
SPARQL (002: "no path values") nor Datalog can do, and the same engine
has 114,962,418 derivations for the two-link join, worked out and not
run. The thesis is exact for RDF and Datalog and loose for RDF and
miniKanren.

*The property graph is not a triple store either.* An edge in Neo4j has
its own identity and its own record. Two OWNS between one pair is legal
(the audit checked there are none). A set of triples cannot say that
without the Holding node.

** What was not tested

- *Open and closed world.* This is the difference usually cited, and
  nothing here measured it. 002 has no RDFS, no OWL, no inference, and no
  =NOT EXISTS= or =MINUS= (I searched =rdf.clj=). 003 has no =not=. Only
  004 used negation: =nafc=, 219 CUSIPs Guggenheim holds and Envestnet
  does not, equal to the set difference. That is negation as failure,
  which is the closed-world reading. As run, all five forms behaved
  closed-world. The one place the distinction showed was finding 24: a
  node key is a closed-world statement, and RDF as loaded here had no way
  to make one. From general knowledge, that is SHACL's job, not OWL's.
- *Merging by global name.* The point of an IRI is that two sources can
  agree on it. 002 says so and adds "nothing here tests that". The
  repository has the test case sitting in its database (see the next
  section) and did not run it.
- *Recursion.* The rule in 003 is not recursive. 004's is, bounded at
  three hops, over a graph where everything is within two links of
  everything. "Nothing in it to search" is 004's own verdict.
- *Time.* The datom's fourth place. DataScript keeps no history (003).

** Verdict

| claim | standing | on what |
|-------+----------+---------|
| a fact is a tuple; a query is a join | exact | six shared numbers, three gates |
| a rule is a named join | exact for Datalog and miniKanren; SPARQL has none | 003, 004 |
| RDF is related to logic programming | exact for Datalog; an analogy for miniKanren | 003 against 004 |
| both are triple stores | wrong for logic programming: arity is free | 004's =holds= |
| identity, schema, index carry across | analogy; each bit differently | the tables above |
| the same query gives the same number | wrong once anything is counted | Asami's sum, pldb's bags |
| open against closed world separates them | not tested here | no inference, one =nafc= |

Reworded so that it is true: triples, datoms and relations are the same
facts under the same joins, and they differ in everything a database adds
to that: arity, identity, multiplicity, constraints and who plans the
query. The property graph differs in the first two as well.
